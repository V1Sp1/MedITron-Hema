# Техническая реализация бэкенда и PDF импорта Hema

Бэкенд — локальный FastAPI-сервис. Он отдаёт сайт, принимает и проверяет входы, извлекает PDF, рассчитывает правило Hb и модели, подбирает фразы и хранит результат. Это руководство описывает фактический код, включая ошибки и границы реализации. Точные примеры контрактов также находятся в `frontend/API_CONTRACT.md`.

## Запуск и жизненный цикл

`backend/__main__.py` разбирает аргументы argparse и создаёт приложение. Uvicorn запускается на 127.0.0.1; порт по умолчанию 8000, access_log отключён. В lifespan создаются RAM Store, research-сеансы, AuthStore и приватная staging-папка; запускается очистка каждые 15 секунд. ModelService загружается через threadpool. При завершении staging удаляется, auth.sqlite3 закрывается, медицинская SQLite :memory: уничтожается. Модель загружается один раз, не для каждого запроса. Отсутствие готовой модели не мешает открыть HTML, но прогноз завершится 503.

| Параметр | Что меняет |
|---|---|
| `--port 8001` | Другой локальный порт; сайт следует открыть на том же порту |
| `--data-dir PATH` | Каталог auth.sqlite3/приватных временных файлов; медзаписи в RAM; приоритет над HEMA_DATA_DIR |
| `--ocr auto` | OCR при непригодном тексте/доминирующем изображении |
| `--ocr off` | Только текст; удобен на Windows |
| `--ocr always` | Попытка OCR всех страниц; только macOS |
| `--freshness-policy policy.json` | Явная политика максимальной давности по показателям |
| `--phrase-file phrases.json` | Согласованный legacy-файл следующих шагов |
| `--model-bundle PATH` | Другие доверенные локальные веса |
| `--no-model` | Явное отключение модели; только Hb и общие пояснения |

`--model-bundle` и `--no-model` взаимоисключающие. Для freshness policy значение — целое неотрицательное число дней, ключ — известный analyte. По умолчанию `{}`: клинические сроки не придуманы.

## Состав модулей

app.py собирает middleware, модели тел запросов, маршруты и orchestration. features.py читает схему, проверяет числа, переводит совместимые единицы, создаёт черновик формы и предупреждения. screening.py вычисляет Hb и базовую структуру отчёта. model_service.py дополняет её обученными scores и решениями. verdicts.py проверяет согласованность. data_sufficiency.py оценивает покрытие; recommendations.py выбирает тексты. store.py хранит JSON-объекты и ревизии. parser_service.py запускает worker с таймаутом; parse_worker.py превращает файл задания в результат вызова lab_parser.

## API

| Метод | Вход и действие | Сохраняет данные |
|---|---|---|
| GET /api/health | Готовность, OCR, лимиты, версия | Нет |
| GET /api/features | Словарь 37 входов и единицы | Нет |
| GET /api/models/status | ready/unavailable/disabled, версия, выбранные модели | Нет |
| POST /api/observations/pdf | Multipart files, пакет PDF → наблюдение и форма | Да |
| GET /api/observations/{id} | Наблюдение, кандидаты, предупреждения, ревизия | Нет |
| GET /api/observations/{id}/documents/{document_id} | Оригинал одного PDF | Нет |
| PUT /api/observations/{id}/review | revision и inputs → подтверждение | Да |
| POST /api/patient/predict | inputs и необязательная связь с проверенным PDF | Да, отчёт |
| POST /api/doctor/predict | То же, роль врача | Да, отчёт |
| GET /api/reports/{id} | Сохранённый JSON отчёта | Нет |
| POST /api/recommendations | reportId и совпадающая audience | Нет |
| GET /api/recommendations/catalog | audience → полный каталог роли | Нет |
| POST /api/recommendations/preview | inputs, audience, необязательный verdict | Нет, явная симуляция |
| POST /api/data-sufficiency | Неполные inputs и audience | Нет |

JSON-схема доступна по `/openapi.json`. Swagger/Redoc с внешним CDN отключены. Основной прогноз не принимает verdict от пользователя: разрешены inputs, observationId, observationRevision, reviewedObservation. Тела Pydantic используют strict=True и extra=forbid; неизвестные поля отклоняются.

После явного подтверждения исследовательского режима минимальный ручной запрос:

```json
{"inputs":{"age_years":42,"sex":"F","hemoglobin":108}}
```

Он допустим для проверки Hb, но содержит только один лабораторный показатель: причина/дефициты будут подавлены по sparse policy. Для проверки модели нужна более богатая панель. Audience задаётся маршрутом predict, а не передаваемым произвольным диагнозом.

## Полная цепочка прогноза

1. Проверяется research grant и, для врача, вход. validate_inputs выбирает полный набор 37 ключей, отсутствующие заполняет null, проверяет sex, возраст и числа.
2. screen формирует threshold, anemia, missing, полноту, исходную структуру и предупреждение.
3. При подключённой модели ModelService.apply вызывает inference и проверяет scores; меняет method/source/версию, создаёт modelVerdict и решение с причинами.
4. Для PDF требуется reviewedObservation=true и актуальная observationRevision. Сервер подтверждает входы; неверная ревизия даёт 409. Извлечённые данные не переписываются пользовательской формой.
5. Создаётся UUID reportId/id и createdAt, сохраняется связь с наблюдением и версией словаря.
6. phrases_for_report формирует recommendationSnapshot. Если каталог некорректен, отчёт не сохраняется, возвращается 503.
7. Store сохраняет отчёт. Клиент получает JSON и отдельно запрашивает рекомендации по reportId.

Роль врача и пациента использует одну математическую процедуру, различаются тексты и вид результата. Версия модели и словаря делает сохранённый отчёт прослеживаемым.

## PDF как одно наблюдение

Наблюдение — весь пакет, загруженный одной операцией. Оно не разделяется по датам. Разные даты допустимы, но это не разрешает автоматически выбрать последнее измерение или усреднить повторы. Порядок файлов не задаёт приоритет. До расчёта человек проверяет форму.

API проверяет от 1 до 10 файлов, расширение .pdf, имя длиной до 200 символов, отсутствие нулевого символа и сигнатуру %PDF- в первых 1024 байтах. Лимиты: 20 МиБ на PDF, 60 МиБ суммарно, 100 страниц в документе, 61 МиБ всего HTTP-body с multipart. Ранний content-length и фактический поток body ограничиваются middleware. Копии временно записываются в приватную hema-live-*/{observation UUID}/{index}/analysis-N.pdf. После обработки исходные PDF — RAM BLOB, временная папка удаляется при любом результате. Один пакет обрабатывается одновременно, конкурирующий запрос получает 429. Неудачная загрузка удаляет созданный ею каталог.

Worker запускается командой текущего Python `-m backend.parse_worker` из ROOT. Временный request.json содержит пути, OCR, дату оценки, policy и лимиты; result.json содержит observation. stdout отключён, stderr записывается во временную папку. Через 180 секунд worker завершается. На macOS/Unix прекращается группа процессов; на Windows используется taskkill /T /F с резервным process.kill. Дополнительные лимиты заданы в worker_limits.py: POSIX CPU/файлы/дескрипторы/core; Linux RAM 1 ГиБ; Windows Job Object CPU/память/процессы. На macOS жёсткой RAM-квоты нет; worker не является файловым/сетевым sandbox.

## Слои парсера

`lab_parser/models.py` содержит dataclass-модели Word/Row/Page/Document/Measurement/Observation. `extraction.py` получает текст и таблицы с координатами через pdfplumber и при необходимости MacOSOCR. `catalog.py` нормализует написание и использует версии синонимов из data/analytes.json. `parsing.py` распознаёт числа, знак сравнения, название, единицу, референс, дату, биоматериал и контекст строки. `pipeline.py` объединяет документы, отмечает повторы/возможное несовпадение пациента и создаёт UUID. `cli.py` задаёт параметры и сохраняет JSON.

Native extraction удаляет дублирующиеся символы, группирует слова по вертикальному пересечению и учитывает колонки. Строки внутри распознанной таблицы заменяются actual cells; прочий текст остаётся строками с геометрией. OCR auto включается, когда мало пригодного текста, много битых символов или площадь изображений превышает 40% страницы. Это техническая эвристика, не измеренная гарантия распознавания.

MacOSOCR компилирует Swift-мост через swiftc во временном каталоге один раз на пакет. Apple Vision распознаёт страницы локально; облачный сервис не используется. Ошибка OCR сохраняется как issue, доступный native text не исчезает. На Windows этого OCR нет. `off` означает text-only; сканы получают ocr_required. always не превращает Windows в поддерживаемую OCR-платформу.

## Что сохраняется у измерения

analyte — известный лабораторный ключ либо null. Standalone CLI сохраняет raw_name/raw_value/raw_unit/reference. В server research-потоке они очищаются после нормализации; source.text/context_text и rows страниц также удаляются. value — распознанное число либо null; comparator хранит `<`, `>`, `>=` отдельно. unit — унифицированное написание. collected_on/date_source/age_days/freshness — дата и происхождение. specimen — явно указанное название материала. source содержит document_id, страницу с 1, bbox, метод извлечения и OCR-confidence при наличии. issues/review_status фиксируют необходимость проверки.

Заголовок исследования может стать контекстом вложенной строки «Концентрация»; Standalone CLI сохраняет context_text/context_bbox; сервер оставляет геометрию, удаляет произвольный текст. Дата рождения, выдачи и заказа не подменяет дату забора. Несовпадение явных ФИО/даты рождения — только предупреждение, не полноценная идентификация пациента. Явно указанные моча/кал/слюна не используются как лабораторные признаки крови.

## Нормализация и черновик

CLI извлекает значения и унифицирует запись единиц; conversion в единицы модели выполняет API features.py. Он временно использует raw и добавляет normalized_value/normalized_unit/conversion; перед сохранением API удаляет произвольные raw/source/identity поля. Допускаются размерностные scale-конверсии, например Hb 10.8 g/dL → 108 g/L, ferritin 9 ng/mL → 9 µg/L, MMA 300 nmol/L → 0.3 µmol/L, hematocrit 0.4 L/L → 40%. Масса не переводится в молярную концентрацию по догадке; например creatinine mg/dL остаётся без поддержанной конверсии. Неизвестная единица не определяется по «похожему» числу.

draft_inputs подставляет только единственный кандидат известного analyte с точным числом, совместимой единицей и без stale/future_date. Даже два одинаковых результата считаются повтором и требуют выбора. `<5` не становится точным 5. Возраст и пол не извлекаются для расчёта автоматически. Неизвестные и неподставленные кандидаты сохраняются в полном наблюдении.

## Хранение, владельцы и ревизии

Store использует sqlite3.connect(":memory:"), objects(kind,id,revision,expires,payload) и documents(observation_id,id,payload BLOB). Постоянная медицинская DB не создаётся, историческая hema.sqlite3 не открывается. RLock, allow_nan=False и optimistic revision сохраняются. Лимиты payload 128 МиБ/1000 объектов; update также проверяет рост. Срок не продлевается чтением и не позже часа от подтверждения режима. Просроченные записи недоступны сразу; sweep до 15 секунд. Перезапуск удаляет новые данные.

POST /api/privacy/acknowledge принимает policyVersion/dataKind synthetic|anonymized/researchOnly true и выдаёт закрытую часовую cookie. Это заявление об исследовательском режиме, не медицинское согласие. Перед upload/predict/preview/coverage обязателен grant, иначе 428. Любой observation/report/PDF/read/review/recommendations/delete требует совпадения grantId. Врачебный объект дополнительно требует своего doctorId. Другой пользователь получает 404. Старый объект без _access не выдаётся. Перед сохранением повторно проверяется живой grant, чтобы отзыв во время worker не восстановил данные.

DELETE /api/privacy/session отзывает grant и все его объекты/PDF. DELETE observation удаляет также связанный report и оригиналы; DELETE report сохраняет observation до своего TTL. Вход/выход врача завершает прежний medical-сеанс. Скачанные файлы, печать, swap/резервные копии ОС вне контроля приложения.

AuthStore хранит в auth.sqlite3 логины/организацию/отображаемые имена/хеши/сеансы и хеши API-ключей; данные учётных записей остаются после перезапуска. Сеанс врача до 8 часов, медицинский до 1 часа. Подробности backend/AUTH.md. Исторические копии требуют отдельного решения: backend/privacy_admin.py status / purge-legacy; автоматического уничтожения старых пользовательских источников нет.

Лабораторный POST /api/integration/predict имеет Bearer-ключ организации и строгий research-only контракт; ничего не сохраняет в Store. organizationId берётся из ключа, stored=false/reportId=null. Лимиты 60/min/key и 240/min/process. Создание/отзыв и примеры: backend/INTEGRATIONS.md. Полное описание защиты и остаточных условий: docs/09_SECURITY_REMEDIATION.md.

## Защита локального сервиса и ошибки

TrustedHost разрешает localhost/127.0.0.1. CORS разрешает локальные origins на 8000 и 5173; изменяющие запросы дополнительно проверяют Origin и тот же origin. Loopback ограничивает адрес прослушивания. Роль определяет представление; авторизация врача, research-cookie и проверка владельца выполняются отдельно. Изменения с cookie требуют X-Hema-Client: 1. No-store/CSP/no-referrer/nosniff ограничивают кэш/встраивание.

| Код | Типичная причина | Что сделать |
|---|---|---|
| 400 | Неверный host/body/число multipart-файлов | Проверить запрос и лимиты |
| 403 | Неразрешённый Origin | Пользоваться локальным адресом |
| 404 | Некорректный UUID, отсутствующая запись/документ | Использовать существующий ID |
| 428 | Не подтверждён research-сеанс | Подтвердить допустимый вид данных; реальные пациенты пока не разрешены |
| 507 | RAM Store заполнен | Очистить сеанс или дождаться TTL |
| 409 | Устаревшая ревизия, PDF не подтверждён, другая роль рекомендаций | Повторить проверку/загрузить актуальное состояние |
| 413 | Лимит размера запроса/файла/пакета | Уменьшить размер |
| 422 | Неверные поля, PDF без кандидатов, ошибка worker | Исправить вход или ввести вручную |
| 429 | Уже идёт обработка пакета | Дождаться завершения |
| 503 | Модель/каталог фраз недоступен или некорректен | Проверить weights, библиотеки и JSON |
| 504 | Парсер превысил 180 секунд | Меньший пакет или текстовый PDF |

Не все документы универсально покрыты: переносы названий, многоколонные формы, плохие сканы и рукописный текст требуют ручной проверки. Качество OCR на Lab4U ограничено; интеграция API не улучшает его сама по себе.

## Разработка и диагностика

Начинайте с `/api/health`, `/api/models/status`, `/api/features`. Для воспроизводимой ошибки сохраните обезличенный inputs и версии модели/словаря. Затем найдите соответствующий тест. Python-suite проверяет формат, нормализацию, целостность источников, отдельный worker, ревизии, сохранение, роли, веса и рекомендации. Изменение порогов/модели требует новой оценки качества, прохождения unit-тестов для этого недостаточно.
