# Рабочая сборка baseline_v1 + ферритин v4

Обновление от 2026-10-05. По прямому запросу пользователя в стандартный backend подключён отдельный прогноз низкого ферритина. Клинические case-головы baseline_v1 сохранены. Статус сборки: `baseline_v1_plus_ferritin_v4`; клиническая валидация отсутствует.

## Что изменилось

Hb по-прежнему оценивается правилом кейса. Класс/дефициты и черновые фразы формируются v1 с прежней политикой полноты и воздержания. Новый блок `ferritinScreening` прогнозирует маркер ниже 15 µg/L, если ферритин отсутствует. Он не меняет `modelVerdict`, классы, бинарные дефициты, полноту исходных данных или лечебные фразы. B12/PLP головы v4 в этом API не вызываются и не выводятся.

Если ферритин измерен, блок имеет статус `observed`, показывает `observedValue` и единицу µg/L. Прогноз/score/порог/положительный флаг не рассчитываются; значение 0 также считается измеренным. Это показ результата анализа без нового клинического порогового правила.

## Область применимости

- Женщины 18–49 лет; беременность исключалась в исходных когортах. При `pregnant` прогноз не выполняется.
- Для женщин 18–44 лет при `unknown` прогноз не выполняется. Для 45–49 лет неизвестный статус допускается в соответствии с замороженным протоколом исходной когорты; это не доказательство отсутствия беременности.
- Нужны минимум пять поддержанных лабораторных значений: Hb, RBC, Hct, MCV, MCH, MCHC, RDW, тромбоциты, WBC, креатинин, альбумин, LDH, CRP. Возраст/пол и остальные анализы в этот минимум не входят.
- При наличии креатинина/альбумина/LDH/CRP выбирается `extended`; иначе `cbc`. Например, один B12 не переключает голову ферритина на расширенную панель.
- Все профильные маркеры и целевые метки исключены из предикторов v4. Пропуски остаются неизвестными.

Статус беременности — отдельный контекст запроса; его нельзя помещать в 37 лабораторных входов. Форма сайта спрашивает его отдельно, при импорте новой строки CSV/XLSX выбор сбрасывается в `unknown`; PDF его не распознаёт. Перед расчётом после PDF прежний выбор сохраняется для того же наблюдения.

## API

```json
{
  "inputs": {"age_years":40,"sex":"F","hemoglobin":110,"RBC":4,"hematocrit":33,"MCV":82,"MCH":27.5},
  "pregnancyStatus": "not_pregnant"
}
```

Контекст принимают POST `/api/patient/predict`, `/api/doctor/predict`, `/api/integration/predict`; допустимы `unknown` (по умолчанию), `not_pregnant`, `pregnant`. Действующие требования исследовательского сеанса/авторизации врача/ключа организации сохраняются. Результат хранится вместе с версией весов/порогом и контекстом; лабораторный API остаётся без сохранения записей.

Статусы `ferritinScreening`: `observed`, `research_prediction`, `outside_scope`, `unknown_pregnancy`, `insufficient_data`, `unavailable`, `disabled`. Только `research_prediction` содержит `score`, `decisionThreshold`, `screenPositive`, `route`; это исследовательский score, не клиническая вероятность. Отрицательный прогноз не исключает низкий ферритин или дефицит железа. Пациенту показывается объяснение, врачу дополнительно score и порог. Блок включён в экранный отчёт, печать, PDF и JSON.

GET `/api/models/status` и `/api/health` показывают readiness v1 и отдельного модуля. При ошибке v4 основной inference v1 сохраняется, health имеет статус `degraded`, блок ферритина — `unavailable` без числового score. Ошибка основной v1 по-прежнему даёт 503. Это явное отсутствие дополнительного прогноза, не замена его нормальным анализом.

## Запуск и доверие к весам

Обычный запуск `python -m backend` подключает сборку автоматически. `--no-ferritin-model` отключает отдельный прогноз; `--no-model` отключает оба модельных компонента. `scripts/launch_local.py --check` проверяет оба компонента.

Веса и пороги не переобучались. v1 SHA-256 `b413ce1e45d678f64dd03e3430630e09887b9a89303c534807f6cc78db1e19ef`; v4 `59ffb63213b815500a1030408f9f1b07489625e39e1c81f5dfa1d9cde7b6836f`. v4 загружается только из отдельного реестра `backend/data/biochemical_model_trust.json`: до joblib проверяются размер, хеш весов и хеш свидетельств внешнего теста. Десериализуются те же проверенные байты. Обе головы ферритина должны пройти сохранённые критерии внешней проверки. Единицы/схема/тип голов/пороги и пробный inference проверяются при запуске.

## Качество и проверка

На независимом цикле NHANES 2007–2008, 1254 наблюдения/213 низких маркеров: расширенная v4 F1 0,616, sensitivity 63,4%, specificity 91,4%, precision 60,0%; ОАК F1 0,594. Эти метрики относятся к низкому ферритину в проверенной группе, не к 12 диагнозам и не к целому гибриду. Сравнение с замороженной v1 и разработческими порогами: F1 0,468 расширенная / 0,413 ОАК. Пороги определены до открытия внешнего теста; при интеграции они не подбирались заново.

163 Python-теста и 35 Node-тестов прошли при интеграции. Новые проверки покрывают настоящий inference/пороги обеих панелей, измеренный ферритин, границы возраста/беременность, количество поддержанных лабораторных показателей, неизвестный контекст, отказ при ошибке/непроверенных весах/непройденном критерии, неизменность v1/фраз, сохранение отчёта и лабораторный API. Тесты программы не доказывают клиническую точность. Агрегированные результаты сверки — `experiments/backend_hybrid_v1_v4/verification.json`; отчёт об исходном внешнем качестве — `experiments/biochemical_v4/REPORT.md`.

Сверка завершена: все 3762 прогноза (1254 × три вида ввода) воспроизвели сохранённые scores/маршруты/пороги и метрики, максимальное отличие score менее 1e-12. Backend перезапущен, обе модели ready; браузер и 14 страниц четырёх синтетических PDF проверены. Обновлённый пакет: `deliverables/Hema_project_2026-10-05_hybrid_v1_v4.zip`; прежние архивы сохранены как исторические сборки.

Архив проверен после распаковки через `scripts/verify_handoff.py`: проверены манифест, все комплектные семейства, реальный гибридный inference и unknown, PDF worker, доступ/удаление сеанса и лабораторный API. Свидетельство — `experiments/backend_hybrid_v1_v4/handoff_verification.json` в рабочем проекте. Проверка использует уже установленные зависимости на macOS; Windows здесь не запускался.
