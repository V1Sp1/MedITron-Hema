# Условия допуска медицинского сценария

## Назначение необходимо определить предметно

План пользователя — использование клиниками/врачами и API лабораторий для отчётов пациентам — может включать медицинское назначение. Нельзя считать, что формулировка «не ставим диагноз» автоматически исключает статус медицинского изделия. Оценивать функции, предполагаемое использование, пользователей, влияние отчёта на решение, инструкции и рекламу. Определение включает программное обеспечение при соответствующем назначении. [Статья 38 323-ФЗ](https://www.consultant.ru/document/cons_doc_LAW_121895/ddcfddbdbb49e64f085b65473218611b4bb6cd65/), [Росздравнадзор](https://www.roszdravnadzor.gov.ru/medproducts).

До документированного решения текущий выпуск ограничен исследовательской демонстрацией. Нет флага «разрешить реальных пациентов» и готового публичного клинического режима. Даже действительное согласие на данные не подтверждает клиническую пригодность модели.

## Обязательные результаты перед новым выпуском

- Утверждённое назначение: исследуемые состояния, возраст/группы, разрешённые пользователи, входные панели/единицы, действия на основании результата, противопоказания/ограничения.
- Регуляторное заключение по фактическому продукту; применимые процедуры классификации/регистрации/оценки, сведения о допуске и границы версии. Не присваивать класс риска по одной строке дисклеймера.
- Документированное происхождение обучающих/валидационных данных, законные права и основания использования, раздельность наборов, реестр изменений.
- Независимая клиническая валидация на релевантной популяции/лабораториях, включая пропуски, разные методы/единицы, смешанные дефициты, ошибки OCR, вне области применимости и регрессии по группам.
- Раздельная оценка дискриминации, калибровки, порогов и полезности. Внутренняя OOF-калибровка кейса и хороший F1 не подтверждают вероятность заболевания реального пациента.
- Медицинское утверждение полноты данных, причин воздержания и всех фраз/следующих шагов, а не только отдельных редакционных исправлений. Ответственный специалист, версия, дата, источник, процедура отзыва.
- Контроль риска пропустить заболевание при низком score/нормальном Hb, ложного положительного вывода, неверной принадлежности PDF, ошибочных единиц/дат и автоматической выдачи непроверенного отчёта.
- Документированный review врачом/допустимым пользователем, обучение, инструкции по неопределённости, порядок обращения при ошибке и выпуска исправлений.
- Завершённый правовой контур данных, защищённая инфраструктура, контроль доступа/аудит, модель угроз, нагрузочные проверки и независимое тестирование безопасности.
- Контроль подписанных/доверенных весов и зависимостей, процедуры обновления/отката, мониторинг деградации и запрет обучения на пользовательских запросах без отдельного процесса.

## Что реально реализовано в Hema

Правило Hb из кейса, 37 полей и 35 лабораторных показателей, отдельные модели ОАК/расширенной панели, строгая схема, контроль пропусков, структурированного вердикта и противоречий. При скудном вводе специфические выводы подавляются. Каталоги фраз имеют статус draft. Default baseline_v1 не откалиброван; отдельный calibrated_v3 содержит частичную калибровку по кейсу, clinicalValidated=false. Низкий score не исключает дефицит.

UI/PDF отображают оценки 0–1 с ограничениями; API имеет канонические поля deficiencyScores/anemiaScores и scoreMeaning. Legacy-поля с названием probability оставлены для совместимости, они не являются заявлением о клинической вероятности. Каждый API-отчёт указывает researchOnly=true и clinicalUseEnabled=false. Эти меры уменьшают вводящие в заблуждение утверждения, но не заменяют перечисленные результаты допуска.
