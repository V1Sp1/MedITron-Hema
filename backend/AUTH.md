# Вход для врача Hema

Врачебный режим требует учётную запись организации. При выборе «Я врач» открывается окно с логином, паролем, показом/скрытием пароля, описанием получения доступа и восстановлением через администратора. Прямой переход на doctor.html тоже запрашивает вход. Самостоятельной регистрации и отправки пароля по почте нет. Пациенту пароль не нужен; требуется отдельный исследовательский часовой сеанс и подтверждение допустимого вида данных.

## Управление учётными записями

Команды выполняет администратор на компьютере сервера из корня проекта:

```sh
.venv/bin/python -m backend.accounts create ivan.petrov --name "Иван Петров"
.venv/bin/python -m backend.accounts list
.venv/bin/python -m backend.accounts reset-password ivan.petrov
.venv/bin/python -m backend.accounts disable ivan.petrov
.venv/bin/python -m backend.accounts enable ivan.petrov
```

На Windows используйте `.venv\Scripts\python.exe` вместо `.venv/bin/python`. Пароль вводится в терминале дважды, без отображения; его не передают аргументом команды. Создание не перезаписывает существующий логин. Отключение, включение и смена пароля завершают предыдущие сеансы. Данные для входа выдаёт администратор отдельно.

Логин: 3–64 символа, латиница/цифры и `_.@-`, без учёта регистра. Пароль: 15–128 символов; пробелы и Unicode допустимы. `--data-dir PATH` указывается **перед** командой, если сервер использует другой каталог; поддерживается также HEMA_DATA_DIR.

## Хранилище и сеансы

База — `data/local/auth.sqlite3` (или выбранный data-dir). В users хранятся UUID, логин, индивидуально посоленный scrypt-хеш, отображаемое имя, признак активности и дата создания. Исходные пароли не сохраняются и не восстанавливаются: администратор задаёт новый. В sessions хранятся SHA-256-хеш случайного токена, ID записи и срок истечения; в attempts — кратковременные счётчики входа. База переживает перезапуск, исключена из Git/переносимого архива и недоступна статическому сайту. Права файла на POSIX — 0600.

Сеанс: до 8 часов, HttpOnly cookie с SameSite=Strict. Новый вход заменяет текущий токен; выход удаляет его на сервере и в браузере. На HTTPS добавляется Secure; текущий локальный loopback-сервер работает по HTTP. Секреты не записываются в localStorage. Cookie действует на один hostname: localhost и 127.0.0.1 — отдельные адреса входа. Dev-сервер использует API на том же hostname, порту 8000, с credentials/include.

После пяти неуспешных попыток для одного логина или тридцати для одного сетевого адреса за 15 минут — 429. Неизвестная, отключённая запись и неверный пароль получают одинаковое сообщение. Изменение данных с cookie требует X-Hema-Client: 1; чужие Origin отклоняются. Проверка пароля — scrypt N=131072, r=8, p=1; ориентир: [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).

## API и границы доступа

- GET /api/auth/session → `{authenticated, user}`; user содержит id, username, displayName, expiresAt (Unix seconds), без хеша/пароля/токена.
- POST /api/auth/login → `{username, password}`, заголовок X-Hema-Client: 1; возвращает профиль и устанавливает cookie. 401 — неверные данные; 429 — ограничение попыток; 422 — некорректный запрос без отражения пароля.
- POST /api/auth/logout → `{}`, тот же заголовок; завершает текущий сеанс.

Все новые объекты закрыты проверкой research-cookie; врачебные дополнительно требуют своего doctorId. Другая запись получает 404. Старые объекты без _access закрыты; историческая disk hema.sqlite3 не открывается новой программой.

При загрузке PDF передаётся audience=doctor|patient. Doctor требует входа. В обоих случаях объект связан с закрытым research-сеансом до часа; UUID не предоставляет доступ. Physician-session до 8 часов не продлевает медицинский TTL. Logout/login отзывает прежний medical grant и удаляет его записи/PDF.

При выходе врачебный интерфейс очищается переходом на главную. При истечении сеанса или отказе API — повторный вход; старые введённые данные не передаются другой учётной записи. Данные для входа не предоставляются публичным API управления пользователями: администрирование локальное.

Реализованы прикладная принадлежность организации/врача/часового сеанса и краткий журнал действий в RAM. SSO/MFA, промышленная изоляция, системный аудит и веб-администрирование пока отсутствуют. Логины/отображаемые имена тоже могут быть персональными данными: исследовательские аккаунты делайте вымышленными, основание сотрудника и сроки оформляет будущий оператор.
## Несколько организаций

Создайте test-организацию через backend.integrations organization-create, затем accounts create LOGIN --organization ID. По умолчанию local-research — вымышленный research-контур, не юридический оператор. organizationId хранится с пользователем и приходит в профиль. Логины уникальны для всего экземпляра. API-key относится к одной организации и не даёт доступ к browser report. Подробности: INTEGRATIONS.md.
